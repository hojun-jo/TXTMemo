# Feature 04. 닫기 시 저장 확인 플로우

## 1. Idea Summary

이 기능은 사용자가 창 닫기 또는 앱 종료를 시도할 때 현재 문서 상태를 판정해 `즉시 종료` 또는 `저장 분기`로 나누는 종료 보호 기능이다. macOS 메모장 MVP에서 이 플로우는 데이터 손실 방지와 빠른 종료 경험을 동시에 책임지며, 여러 문서 창이 열려 있어도 각 창의 내용을 독립적으로 판정해야 한다.

### Feature Name

닫기 시 저장 확인 플로우

### One-sentence Definition

문서가 비어 있거나 이미 저장된 상태면 바로 닫고, 내용이 있으며 미저장 변경이 있을 때만 `저장`, `다른 이름으로 저장`, `취소`, `저장하지 않고 종료`를 제공하는 종료 분기 기능이다.

## 2. Problem This Feature Solves

- 메모장 앱에서 가장 치명적인 실패는 저장되지 않은 내용 손실이다.
- 반대로 모든 종료 시도에 확인 창을 띄우면 메모장의 핵심 가치인 속도가 무너진다.
- 사용자는 종료 시점에 지금 닫아도 되는지, 저장이 필요한지, 새 이름으로 남겨야 하는지를 즉시 판단할 수 있는 명확한 분기를 원한다.
- 여러 문서 창이 열린 상태에서는 어떤 창이 실제로 위험 상태인지 창 단위로 분리해 다뤄야 혼동이 없다.

## 3. Target User And Usage Context

### Who Uses It

- 빠르게 메모를 적고 바로 닫는 일이 잦은 macOS 사용자
- 여러 문서 창을 동시에 띄워 초안과 별도 메모를 병행하는 사용자
- 저장 여부를 종료 직전에 결정하는 단순한 Windows 메모장식 플로우를 기대하는 사용자

### When It Is Used

- 창 닫기 버튼으로 현재 문서를 닫으려 할 때
- `Command+Q`로 앱 전체 종료를 시도할 때
- 메뉴의 종료 액션을 눌렀을 때
- 앱 종료 과정 중 미저장 창이 하나 이상 발견됐을 때

## 4. Feature Concept Definition

### Why It Matters

이 기능이 있어야 앱이 `빠르지만 위험한 편집기`가 아니라 `빠르고 안전한 메모장`으로 성립한다. 또한 MVP의 핵심 경험인 `입력 후 저장 또는 안전한 종료`를 완결시키는 마지막 보호막 역할을 한다.

### Confirmed Requirements

- 창 닫기와 앱 종료는 동일한 종료 판정 규칙을 사용한다.
- 여러 문서 창이 열려 있어도 각 창은 자신의 텍스트, 저장 경로, 미저장 상태를 기준으로 독립 판정한다.
- 공백, 탭, 줄바꿈만 있는 문서는 빈 문서로 간주하고 즉시 종료한다.
- 내용이 있고 미저장 변경이 있으면 4개 선택지를 제공한다.
- 저장 실패 또는 저장 패널 취소 시 종료를 계속 진행하지 않는다.

### Recommended MVP Decisions

- 앱 종료 시 여러 창이 열려 있으면 미저장 창에 대해 확인 UI를 한 번에 여러 개 띄우지 않고 한 창씩 순차 처리한다.
- 순차 처리 순서는 현재 포커스된 창부터 시작해 나머지 열린 창으로 이어지는 방식으로 둔다.
- 확인 UI는 4개 액션이 필요하므로 시스템 기본 3버튼 경고창에 억지로 맞추지 않고 커스텀 sheet 또는 동등한 사용자 정의 확인 UI를 사용한다.
- 종료 판정은 텍스트 trim 결과와 문서의 미저장 변경 여부를 함께 본다. 즉, `빈 텍스트`이거나 `미저장 변경 없음`이면 즉시 종료한다.
- 기존 저장 파일의 내용을 모두 지워 빈 상태가 된 문서도 현재 MVP에서는 빈 문서로 간주해 즉시 종료한다.

### Assumptions

- 문서의 미저장 변경 여부는 [Feature 01. 즉시 입력 가능한 메모 창](./feature-01-instant-note-entry.md)의 편집 상태 모델에서 제공된다.
- `저장`과 `다른 이름으로 저장`의 실제 파일 쓰기 동작은 [Feature 03. `.txt` 저장과 다른 이름으로 저장](./feature-03-txt-save.md) 규칙을 그대로 따른다.
- 종료 시 한글 입력 조합이 끝나지 않았다면 현재 조합 중 텍스트가 손실 없이 커밋되거나 적어도 판정 대상 텍스트에 포함되도록 처리한다.

## 5. MVP Relevance And Priority

### Priority

P0, 필수 기능

### Why It Is In MVP

- 저장 기능만 있고 종료 보호가 없으면 사용자는 가장 흔한 실수 상황에서 데이터를 잃는다.
- `빈 문서는 바로 닫힘`, `작성된 문서는 확인 후 닫힘`이라는 차등 처리 자체가 이 앱의 사용감을 결정한다.
- 여러 문서 창을 지원하는 순간 종료 플로우의 창 단위 판정 규칙을 먼저 고정해야 이후 기능이 흔들리지 않는다.

### Not Included In This MVP Slice

- 미저장 창 목록을 한 화면에 묶어 보여주는 일괄 종료 다이얼로그
- 자동 임시 저장과 종료 후 복구
- 문서별 변경 비교 화면
- 시스템 재부팅, 강제 종료, 크래시 복구 처리

## 6. Main User Flow And Interaction Model

### Flow A. 현재 창 닫기

1. 사용자가 현재 창 닫기를 시도한다.
2. 앱은 현재 창의 텍스트와 미저장 변경 여부를 검사한다.
3. 텍스트가 공백, 탭, 줄바꿈만 있으면 즉시 닫는다.
4. 텍스트가 있고 미저장 변경이 없으면 즉시 닫는다.
5. 텍스트가 있고 미저장 변경이 있으면 종료 확인 UI를 띄운다.
6. 사용자가 `저장`, `다른 이름으로 저장`, `취소`, `저장하지 않고 종료` 중 하나를 선택한다.
7. 선택 결과에 따라 저장 후 닫기, 닫기 취소, 저장 없이 닫기 중 하나로 종료한다.

### Flow B. 앱 종료

1. 사용자가 `Command+Q` 또는 메뉴 종료를 실행한다.
2. 앱은 현재 포커스된 창부터 시작해 열린 모든 문서 창을 순회한다.
3. 비어 있거나 미저장 변경이 없는 창은 즉시 종료 대상으로 처리한다.
4. 미저장 변경이 있는 창이 발견되면 해당 창에만 종료 확인 UI를 띄운다.
5. 사용자가 `취소`를 선택하면 앱 전체 종료를 중단하고, 이미 닫힌 창은 되살리지 않으며 아직 닫지 않은 창들은 유지한다.
6. 사용자가 `저장` 또는 `다른 이름으로 저장`을 선택해 성공하면 해당 창을 닫고 다음 창 판정으로 이동한다.
7. 사용자가 `저장하지 않고 종료`를 선택하면 해당 창을 저장 없이 닫고 다음 창 판정으로 이동한다.
8. 순회가 끝나면 앱 종료를 완료한다.

### Flow C. 확인 UI 내부 분기

1. `저장` 선택 시 현재 경로가 있으면 즉시 저장 후 종료한다.
2. `저장` 선택 시 현재 경로가 없으면 저장 패널을 연다.
3. `다른 이름으로 저장` 선택 시 현재 경로 유무와 관계없이 저장 패널을 연다.
4. 저장이 성공하면 종료를 계속한다.
5. 저장 패널 취소가 발생하면 종료를 중단하고 편집 상태로 복귀한다.
6. 저장 실패가 발생하면 현재 창에 단순 alert를 표시한 뒤 종료를 중단하고 편집 상태로 복귀한다.
7. `취소`는 파일 시스템에 아무 작업도 하지 않고 편집 상태를 유지한다.
8. `저장하지 않고 종료`는 파일 시스템에 아무 작업도 하지 않고 종료를 계속한다.

### Dialog Contract

| 항목        | 정의                                                                                                               |
| ----------- | ------------------------------------------------------------------------------------------------------------------ |
| 표시 조건   | 내용 있음 + 미저장 변경 있음                                                                                       |
| 비표시 조건 | 빈 문서 또는 저장된 상태에서 변경 없음                                                                             |
| 액션        | `저장`, `다른 이름으로 저장`, `취소`, `저장하지 않고 종료`                                                         |
| 버튼 배치   | 좌측에는 `저장하지 않고 종료`를 분리 배치하고, 우측 액션 그룹에는 `취소`, `다른 이름으로 저장`, `저장` 순서로 둔다 |
| 강조 규칙   | `저장`은 primary, `저장하지 않고 종료`는 destructive, `취소`와 `다른 이름으로 저장`은 secondary로 표시한다         |
| 기본 포커스 | 기본 포커스와 Return 기본 동작은 `저장`에 두고, Escape는 `취소`로 매핑한다                                         |
| 허용 개수   | 한 번에 하나의 종료 확인 UI만 활성화                                                                               |
| 종료 재진입 | 동일 창에서 종료 확인 UI가 떠 있는 동안 추가 종료 시도는 무시하거나 기존 UI에 포커스 복귀                          |

## 7. Inputs, Outputs, And States

### Required Inputs Or Conditions

- 종료 의도 종류: 현재 창 닫기 또는 앱 종료
- 현재 문서 텍스트
- 현재 문서의 저장 경로 유무
- 현재 문서의 미저장 변경 여부
- 종료 확인 UI에서의 사용자 선택값
- 저장 패널 결과와 파일 저장 성공 여부

### Expected Outputs Or System Responses

- 현재 창 닫기 또는 앱 종료 진행
- 편집 상태 유지
- 저장 성공 후 종료 또는 저장 실패 후 복귀
- 사용자에게 보이는 오류 메시지
- 종료 중인 창과 계속 열려 있는 창의 명확한 상태 분리

### State Matrix

| 문서 상태                         | 텍스트 상태 | 미저장 변경 여부 | 종료 시 반응      |
| --------------------------------- | ----------- | ---------------- | ----------------- |
| 새 문서, 아무 내용 없음           | 비어 있음   | false 또는 true  | 즉시 종료         |
| 저장된 문서, 변경 없음            | 내용 있음   | false            | 즉시 종료         |
| 저장된 문서, 미저장 변경 있음     | 내용 있음   | true             | 종료 확인 UI 표시 |
| 저장 경로 없는 새 문서, 내용 있음 | 내용 있음   | true             | 종료 확인 UI 표시 |
| 기존 파일 내용을 모두 지운 문서   | 비어 있음   | true             | 즉시 종료         |

### Runtime States

- 종료 요청 대기 상태
- 문서 판정 상태
- 종료 확인 UI 표시 상태
- 저장 패널 표시 상태
- 저장 진행 상태
- 종료 완료 상태
- 저장 실패 후 편집 복귀 상태
- 종료 취소 후 편집 복귀 상태

## 8. Business Rules And Failure Handling

### Exit Decision Rules

- 공백, 탭, 줄바꿈만 포함한 텍스트는 빈 문서로 간주한다.
- 빈 문서는 미저장 변경 여부와 관계없이 즉시 닫는다.
- 내용이 있고 미저장 변경이 없으면 즉시 닫는다.
- 내용이 있고 미저장 변경이 있으면 종료 확인 UI를 띄운다.
- 종료 확인 UI는 창 단위로만 동작하며 다른 창 상태를 한 번에 섞어 보여주지 않는다.

### Save Branch Rules

- `저장`은 현재 경로가 있으면 즉시 저장하고 종료한다.
- `저장`은 현재 경로가 없으면 저장 패널을 연 뒤 성공 시 종료한다.
- `다른 이름으로 저장`은 항상 저장 패널을 연 뒤 성공 시 종료한다.
- `저장하지 않고 종료`는 디스크에 아무 것도 쓰지 않고 종료한다.
- `취소`는 종료를 중단하고 현재 창을 그대로 유지한다.

### Dialog Presentation Rules

- 종료 확인 UI의 우측 액션 그룹은 `취소`, `다른 이름으로 저장`, `저장` 순서로 배치한다.
- `저장하지 않고 종료`는 다른 액션과 간격을 두고 좌측에 분리 배치한다.
- `저장`은 시각적으로 가장 강한 primary 버튼이며 기본 포커스를 가진다.
- `저장하지 않고 종료`는 destructive 스타일을 사용하되 기본 포커스를 받지 않는다.
- Escape 입력은 항상 `취소`와 동일하게 동작한다.

### App Quit Sequencing Rules

- 앱 종료는 열린 창 각각에 동일한 규칙을 적용한다.
- 앱 종료 시 창 순회는 현재 포커스된 창부터 시작한다.
- 이미 즉시 종료 가능한 창은 확인 UI 없이 닫을 수 있다.
- 미저장 창이 여러 개여도 확인 UI는 동시에 여러 개 띄우지 않는다.
- 어느 한 창에서 `취소`가 선택되면 이미 닫힌 창은 되살리지 않고, 남은 창들에 대한 종료 절차만 중단한다.

### Validation And Error Handling

- 저장 패널을 취소하면 종료를 중단한다.
- 저장 실패 시 오류를 보여주고 종료를 중단한다.
- 저장 실패 시 오류는 종료 확인 sheet 내부에 누적하지 않고 별도의 단일 alert로 보여준다.
- 저장 실패 alert를 닫으면 종료 플로우는 취소된 것으로 간주하고 편집 상태로 복귀한다.
- 저장 실패 alert에는 실패 요약과 가능하면 시스템이 제공하는 원인 문구를 함께 표시한다.
- 종료 확인 UI가 중복 생성되면 안 된다.
- 종료 판정 직전에 IME 조합 중인 텍스트가 누락되지 않도록 편집 버퍼를 동기화해야 한다.

## 9. Edge Cases, Dependencies, And Product Implications

### Edge Cases

- 한글 입력 조합 중 종료 시도 시 현재 조합 문자가 판정에서 누락되면 안 된다.
- 이미 한 번 저장된 파일의 내용을 전부 지운 경우에도, 현재 MVP에서는 빈 문서로 보고 바로 종료한다.
- 변경 없는 창은 다른 창의 미저장 여부와 관계없이 즉시 닫힐 수 있어야 한다.
- 앱 종료 도중 어떤 창에서 저장 실패 또는 `취소`가 발생하면 이미 닫힌 창은 되살리지 않고, 남은 종료 절차만 중단한다.
- 사용자가 종료 확인 UI를 띄운 상태에서 다시 닫기 또는 종료를 반복 입력해도 추가 UI가 생기면 안 된다.

### Dependencies

- [Feature 03. `.txt` 저장과 다른 이름으로 저장](./feature-03-txt-save.md)의 저장 결과에 따라 종료 여부가 결정된다.
- [Feature 01. 즉시 입력 가능한 메모 창](./feature-01-instant-note-entry.md)의 현재 텍스트, 미저장 변경 여부, IME 반영 상태가 필요하다.
- 창 제목의 `*` 미저장 표시 규칙과 종료 판정 규칙이 서로 어긋나지 않아야 한다.

### Product Implications

- 4개 액션을 유지하려면 기본 macOS 3버튼 경고창만으로는 UX가 어색할 수 있어, 커스텀 확인 UI 설계가 필요하다.
- 종료 플로우가 불안정하면 저장 기능 자체보다 더 강하게 신뢰를 손상시키므로 MVP에서도 수동 검증 우선순위가 높다.
- `빈 문서는 바로 종료` 규칙은 속도에는 유리하지만, 사용자가 의도적으로 내용을 모두 지운 뒤 다시 저장할 기회를 기대하는 경우와 충돌할 수 있다.
- 저장 실패를 sheet 내부 상태로 누적하지 않고 alert로 분리하면 종료 확인 UI 상태 관리가 단순해지고, [Feature 03. `.txt` 저장과 다른 이름으로 저장](./feature-03-txt-save.md)의 실패 처리 규칙과도 일치한다.

## 10. Recommendation And Next Decision

### Recommendation

MVP에서는 현재 규칙을 유지하되, 앱 종료 시 미저장 창을 한 번에 나열하지 않고 한 창씩 순차 확인하는 방식이 가장 단순하고 구현 리스크가 낮다. 또한 4개 액션은 제품 의도상 유지하는 편이 맞으므로, 구현 단계에서는 기본 alert에 억지로 맞추기보다 커스텀 sheet를 전제로 설계하는 것이 적절하다. 버튼 배치는 `저장하지 않고 종료`를 좌측에 분리하고, 우측 액션 그룹은 `취소`, `다른 이름으로 저장`, `저장` 순서로 두는 편이 가장 명확하다. 기본 포커스는 `저장`에 두고 Escape를 `취소`로 매핑하면 데이터 손실을 피하면서도 빠른 종료 흐름을 유지할 수 있다. 저장 실패 표현은 sheet 내부 오류 상태보다 단순 alert가 MVP 범위에 더 적합하다.

### Resolved Decisions

- 종료 확인 UI는 커스텀 sheet로 두고, `저장하지 않고 종료`를 좌측에 분리 배치한다.
- 우측 액션 그룹은 `취소`, `다른 이름으로 저장`, `저장` 순서로 배치한다.
- 기본 포커스와 Return 기본 동작은 `저장`, Escape는 `취소`로 둔다.
- 저장 실패는 종료 확인 sheet 내부가 아니라 별도의 단순 alert로 보여주고, alert 확인 후 편집 상태로 복귀한다.

### Next Decision

현재 문서 기준 추가 오픈 질문 없음.

### Suggested Acceptance Criteria

- 내용이 비어 있는 문서는 닫기 시 확인 UI 없이 즉시 종료된다.
- 내용이 있고 미저장 변경이 있으면 정확히 4개 선택지를 가진 종료 확인 UI가 표시된다.
- 종료 확인 UI에서 `저장하지 않고 종료`는 좌측에 분리 배치되고, 우측 액션 그룹은 `취소`, `다른 이름으로 저장`, `저장` 순서로 표시된다.
- 종료 확인 UI의 기본 포커스와 Return 기본 동작은 `저장`, Escape는 `취소`에 연결된다.
- `저장`은 저장 성공 후 종료하고, 저장 패널 취소 또는 저장 실패 시 종료하지 않는다.
- `다른 이름으로 저장`은 새 경로 저장 성공 후 종료하고, 취소 또는 실패 시 종료하지 않는다.
- `취소`는 종료를 중단하고 현재 편집 상태를 유지한다.
- `저장하지 않고 종료`는 파일 시스템에 쓰지 않고 종료한다.
- 저장 실패 시 종료 확인 sheet 내부에 오류를 남기지 않고 별도의 alert를 표시한 뒤 편집 상태로 복귀한다.
- 앱 종료 시 미저장 창이 여러 개 있어도 확인 UI는 한 번에 하나씩만 표시된다.
