# macOS 메모장 앱 실행 체크리스트

## 1. 목적

이 문서는 AppKit 기반 macOS 메모장 앱을 실제로 구현할 때 사용하는 작업용 체크리스트다. 아키텍처 문서와 기능 문서의 결정을 유지한 상태에서, 각 작업 단위를 `구현 -> 테스트 -> 수정 -> 리뷰 -> 수정 -> 리팩토링 -> 재테스트` 순서로 반복하기 위한 운영 기준을 정의한다.

함께 보는 문서:

- [macos-notepad-architecture.md](./macos-notepad-architecture.md)
- [macos-notepad-mvp-plan.md](./macos-notepad-mvp-plan.md)
- [features/](./features/)

## 2. 작업 단위 규칙

- 한 번에 큰 범위를 밀어 넣지 않는다.
- 각 반복 루프는 별도 브랜치에서 시작한다.
- 작업 단위는 `기능 1개` 또는 `하위 시나리오 1개` 수준으로 자른다.
- 각 작업 단위는 완료 시점에 반드시 커밋한다.
- 각 반복 루프는 검증이 끝나면 `develop` 브랜치에 머지하고 종료한다.
- 각 작업 단위는 acceptance criteria로 종료 조건을 명확히 확인할 수 있어야 한다.
- AppKit 문서 구조, responder chain, 창별 세션 상태 분리 원칙을 깨는 변경은 작은 단위로 더 잘게 나눈다.

## 3. 반복 실행 루프

각 작업 단위마다 아래 순서로 반복한다.

1. 브랜치 생성
2. 구현
3. 테스트
4. 수정
5. 리뷰(별도 에이전트)
6. 수정
7. 리팩토링(별도 에이전트)
8. 재테스트
9. 커밋
10. `develop` 머지

다음 작업으로 넘어가기 전에 반드시 이 루프를 닫는다.

## 4. 작업 시작 체크리스트

- [ ] 이번 반복 루프용 브랜치 이름을 정했다.
- [ ] 이번 반복 루프를 별도 브랜치에서 시작했다.
- [ ] 현재 작업 범위를 `macos-notepad-architecture.md`의 계층 책임과 연결했다.
- [ ] 현재 작업 범위를 해당 `features/` 문서의 acceptance criteria와 연결했다.
- [ ] 이번 반복에서 건드릴 레이어를 명시했다. 예: `App`, `Document`, `Editor`, `Workflows`, `Infrastructure`.
- [ ] 이번 반복의 종료 조건을 한 문장으로 적었다.
- [ ] 저장, 종료, IME, undo/redo, wrap, 다중 창 중 어떤 리스크가 있는지 미리 확인했다.

## 5. 구현 체크리스트

- [ ] 최소 구현만 먼저 추가했다.
- [ ] `NSDocument`, `NSTextView`, `NSWindowController`, `NSViewController` 중심의 AppKit 구조를 유지했다.
- [ ] 문서 파일 상태와 창별 세션 상태를 섞지 않았다.
- [ ] responder chain을 우회하는 임시 전역 상태나 과한 브리지를 추가하지 않았다.
- [ ] 새로운 추상화, 공용 헬퍼, 프로토콜은 실제 중복이나 재사용 필요가 확인될 때만 추가했다.
- [ ] 변경 범위 밖의 설계까지 한 번에 확장하지 않았다.

## 6. 테스트 체크리스트

- [ ] 구현 직후 관련 단위 테스트를 추가하거나 갱신했다.
- [ ] 순수 규칙 변경이면 단위 테스트로 고정했다.
- [ ] 계층 연결이 있는 변경이면 통합 테스트 또는 수동 QA 시나리오까지 확인했다.
- [ ] 저장 후 dirty 상태, 제목 `*`, 파일 URL, 종료 분기 같은 문서 앱 핵심 동작을 확인했다.
- [ ] IME, 긴 한 줄, no-wrap 수평 스크롤, undo/redo 같은 편집기 품질 리스크를 확인했다.

## 7. 수정 체크리스트

- [ ] 테스트 실패나 수동 QA 이슈를 바로 수정했다.
- [ ] 같은 실패가 다시 나지 않도록 테스트를 보강했다.
- [ ] 증상만 가리는 임시 분기 대신 원인 레벨에서 수정했다.
- [ ] 수정 후 관련 테스트와 QA를 다시 실행했다.

## 8. 리뷰 체크리스트

이 단계는 반드시 `별도 리뷰 에이전트`로 수행한다.

- [ ] 리뷰 범위를 현재 작업 단위와 관련 파일로 제한했다.
- [ ] 리뷰 요청 시 버그, 회귀 위험, 누락된 테스트, 아키텍처 이탈 여부만 보도록 명시했다.
- [ ] 리뷰 결과 중 실제 이슈만 선별했다.
- [ ] 선별된 이슈를 수정한 뒤 테스트와 QA를 다시 돌렸다.

리뷰 에이전트에 줄 기준:

- 문제 탐지에 집중한다.
- 요약보다 findings를 우선한다.
- 코드 스타일 취향보다 동작 리스크와 누락 검증을 우선한다.

## 9. 리팩토링 체크리스트

이 단계는 반드시 `별도 리팩토링 에이전트`로 수행한다.

- [ ] 리팩토링 범위를 현재 변경 단위 안으로 제한했다.
- [ ] 동작 보존을 전제로 구조 단순화, 책임 정리, 이름 개선, 중복 제거만 검토했다.
- [ ] 불필요한 계층 추가나 과한 추상화는 거부했다.
- [ ] 리팩토링 후 관련 테스트와 QA를 다시 실행했다.

리팩토링 에이전트에 줄 기준:

- 리뷰 역할과 섞지 않는다.
- 새 기능 추가가 아니라 기존 코드 단순화에 집중한다.
- AppKit 문서 앱 구조를 더 선명하게 만드는 방향만 허용한다.

## 10. 완료 체크리스트

- [ ] `브랜치 생성 -> 구현 -> 테스트 -> 수정 -> 리뷰 -> 수정 -> 리팩토링 -> 재테스트 -> 커밋 -> develop 머지` 루프가 닫혔다.
- [ ] 현재 작업 단위의 acceptance criteria를 충족한다.
- [ ] 앱이 실행 가능한 상태다.
- [ ] 문서 앱 핵심 동작 회귀가 없다.
- [ ] 변경이 아키텍처 결정이나 기능 계약에 영향을 주면 `docs/`도 함께 갱신했다.
- [ ] 현재 작업 단위 변경만 포함한 커밋을 만들었다.
- [ ] 커밋 메시지가 작업 단위와 검증 범위를 드러내도록 작성됐다.
- [ ] 현재 작업 브랜치를 `develop`에 머지했다.
- [ ] 머지 후 `develop` 기준으로 다시 실행 가능 상태를 확인했다.
- [ ] 다음 작업 단위로 넘어가도 되는 상태라는 검증 근거를 남겼다.

## 11. 권장 작업 순서

리스크가 큰 순서대로 아래 순서를 권장한다.

1. `NSDocument` 기반 새 문서/파일 열기/다중 창 셸 구축
2. `NSTextView` 기반 plain text 편집기 연결과 first responder 자동 포커스
3. 저장/다른 이름으로 저장과 title dirty 표시 연동
4. 종료 확인 sheet와 앱 종료 순차 처리
5. 글자 크기 조절과 앱 기본 글자 크기 설정
6. auto word wrap on/off와 수평 스크롤
7. undo/redo, IME, empty-close 규칙 집중 QA

## 12. 금지 사항

- SwiftUI 중심 구조로 다시 되돌아가는 구현
- `TextEditor` 제약을 우회하기 위한 임시 브리지 누적
- 문서 내용과 창별 보기 상태를 같은 모델에 저장하는 방식
- 테스트 없이 저장/종료 플로우를 크게 바꾸는 작업
- 리뷰와 리팩토링을 같은 에이전트 역할로 섞는 운영
- 별도 브랜치 없이 여러 작업 단위를 한 흐름으로 섞는 작업
- 여러 작업 단위를 하나의 커밋으로 뭉개는 작업
- 검증이나 커밋 없이 작업 브랜치를 `develop`에 머지하는 작업
